# API Reference

Full interactive docs (generated by FastAPI from the actual route/schema definitions) are always
available at `http://localhost:8000/docs` (Swagger UI) and `/redoc`. This file gives a narrative
overview and copy-pasteable examples; treat `/docs` as the source of truth for exact field types.

All endpoints are under `/api`. Authenticated endpoints require `Authorization: Bearer <token>`.

## Auth

```bash
curl -X POST http://localhost:8000/api/auth/login -H "Content-Type: application/json" -d '{
  "tenant_code": "acme", "email": "admin@acme.io", "password": "DemoAdmin123!"
}'
# -> {"access_token": "...", "refresh_token": "...", "token_type": "bearer"}

curl -X POST http://localhost:8000/api/auth/refresh -H "Content-Type: application/json" \
  -d '{"refresh_token": "..."}'

curl http://localhost:8000/api/auth/me -H "Authorization: Bearer $TOKEN"
```

## Database connections

```
POST   /api/database-connections                       tenant admin only
GET    /api/database-connections
GET    /api/database-connections/{id}
PUT    /api/database-connections/{id}                   tenant admin only
DELETE /api/database-connections/{id}                   tenant admin only
POST   /api/database-connections/{id}/test              tenant admin only
POST   /api/database-connections/{id}/sync-schema       tenant admin only
GET    /api/database-connections/{id}/schemas
GET    /api/database-connections/{id}/tables?schema_name=...
```

`database_type` must be one of `postgresql`, `mysql`, `sqlserver`. The response never includes a
password field, encrypted or otherwise.

## Permissions

```
GET  /api/database-connections/{connection_id}/permissions                 tenant admin only
POST /api/database-connections/{connection_id}/permissions                 tenant admin only
GET  /api/database-connections/{connection_id}/permissions/allowed-schema  any authenticated user
```

`POST .../permissions` body: exactly one of `role_id`/`user_id`, plus `table_id`, `can_read`,
optional `row_filter` (`{"column": "status", "op": "=", "value": "paid"}`, operators: `=`, `!=`,
`<`, `<=`, `>`, `>=`, `in`), and optional `column_permissions` (`can_read`, `mask_type`:
`none`/`full`/`partial`).

`GET .../allowed-schema` returns exactly what the *caller's own* permissions resolve to — the same
shape the LLM prompt is built from. Useful to verify a grant took effect without guessing.

## Files & knowledge bases

```
POST   /api/knowledge-bases
GET    /api/knowledge-bases
POST   /api/knowledge-bases/{id}/files      multipart, field name "uploads" (multiple allowed)
POST   /api/files/upload                    multipart, field "upload" + optional "knowledge_base_id"
GET    /api/files?knowledge_base_id=...
GET    /api/files/{id}
DELETE /api/files/{id}
POST   /api/files/{id}/reprocess
```

Supported extensions: `.pdf`, `.docx`, `.xlsx`, `.csv`, `.txt`. Processing is asynchronous
(Celery); poll `GET /api/files/{id}` for `processing_status`
(`pending` → `processing` → `completed`/`failed`).

```bash
curl -X POST http://localhost:8000/api/files/upload -H "Authorization: Bearer $TOKEN" \
  -F "upload=@sample_data/sample_contract.pdf" -F "knowledge_base_id=$KB_ID"
```

## Chat

```
POST /api/chat
POST /api/chat/stream
GET  /api/messages/{id}/citations
GET  /api/messages/{id}/sql
```

Request:

```json
{
  "conversation_id": null,
  "message": "Compare the total paid invoice value in the database with the approved contract value in the uploaded contract.",
  "database_connection_ids": ["<connection-uuid>"],
  "knowledge_base_ids": ["<kb-uuid>"],
  "stream": false
}
```

Response (`POST /api/chat`):

```json
{
  "message_id": "...",
  "conversation_id": "...",
  "answer": "Database finding:\nThe total paid invoice value in the database is $54,000.00.\n\nDocument evidence:\nThe approved contract value is $60,000.00 EGP, as stated on page 2 of the sample contract.\n\nCombined conclusion:\n...",
  "intent": "hybrid",
  "sources_used": ["database", "documents"],
  "sql": {
    "query_execution_id": "...",
    "query": "SELECT SUM(invoice_value) AS total_paid_invoice_value FROM invoices WHERE status = 'paid' LIMIT 500",
    "row_count": 1
  },
  "citations": [
    {"type": "database", "query_execution_id": "...", "tables": ["invoices"]},
    {"type": "document", "file_name": "sample_contract.pdf", "page": 2, "chunk_id": "...", "relevance_score": 0.73}
  ]
}
```

This is a real, live captured example (not hand-written) — see `IMPLEMENTATION_PLAN.md` and the
session's Phase 6 validation for how it was produced.

`intent` is one of `general`, `database`, `document`, `hybrid`, `clarification`.

### Streaming

`POST /api/chat/stream` takes the same request body and returns `text/event-stream`:

```
event: status
data: {"stage": "classifying_request"}

event: intent
data: {"intent": "hybrid"}

event: source
data: {"source": "database"}

event: sql
data: {"query_execution_id": "...", "query": "...", "row_count": 1}

event: citation
data: {"type": "document", "file_name": "sample_contract.pdf", "page": 2, ...}

event: token
data: {"text": "Database "}

event: completed
data: {"message_id": "...", "conversation_id": "..."}
```

`token` events are the full answer split word-by-word (the underlying Ollama call is
non-streaming), not a true incremental LLM stream — still a real SSE stream carrying every event
type the assignment's contract requires. On any server-side error, an `error` event is emitted
instead of a stack trace: `{"code": "INTERNAL_ERROR", "message": "..."}`.

## Error envelope

Every error response has this shape:

```json
{"error": {"code": "SQL_VALIDATION_FAILED", "message": "The generated query could not be executed safely.", "request_id": "..."}}
```

Common `code` values: `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION_ERROR`, `CONFLICT`,
`SQL_VALIDATION_FAILED`, `CONNECTION_TEST_FAILED`, `LLM_UNAVAILABLE`, `INTERNAL_ERROR`.
